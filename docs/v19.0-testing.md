# osCommerce 19.0 testing

## Scope and source decision

Debian 13 Trixie does not package osCommerce. The appliance therefore uses the
official osCommerce v4 GitHub source at commit
`48d31a361b614cfa66e505d4e8345afd9e30ad79`. The source identifies itself as
osCommerce 4.14.63493. The build downloads a commit-specific archive and
verifies its SHA-256 digest,
`bc3916d1e41ab992f86a2bd56bdc65786c70974686ae312f8814b2083a78ea84`,
before extraction.

Apache, PHP 8.4, MariaDB, Postfix and all PHP modules come from signed Debian
Trixie repositories. Webmin and its Apache, PHP and MariaDB modules come from
the signed TurnKey Trixie repository.

The maintained application update path is the System update section of the
built-in osCommerce App Shop. The official GitHub `main` branch is also
queried without modifying the installed appliance so administrators can see
the upstream source candidate. Debian and TurnKey components remain managed
through APT.

```sh
TKLDEV_CONTAINER=tkldev19-wave2 \
TKL_HARNESS_STATE_DIR=/home/agent/.local/state/turnkey-v19-harness-wave2 \
TKL_HARNESS_LOCK_FILE=/home/agent/.local/state/turnkey-v19-harness-wave2/build.lock \
/sandboxed-git/turnkey/tools/test-v19-appliance oscommerce \
    --source /home/agent/.local/worktrees/turnkey-apps/oscommerce/wish-oscommerce-v19-trixie
```

The command builds the Trixie root filesystem, imports the configured root
into Docker, boots the normal systemd and firstboot path, then runs
`tests/v19.sh`.

## Cheap Trixie probes

A disposable `debian:trixie-slim` container proved the official source on PHP
8.4, MariaDB 11.8 and Apache 2.4 before an exact build. The installer created
the administrator and 75 sample products. The catalog rendered, the
administrator login succeeded, and a real product edit returned HTTP 200,
persisted in MariaDB and appeared on the public product page.

The original v18 download URL returned HTTP 403 through a Cloudflare browser
challenge. This is why v19 uses the pinned official GitHub source archive.

## Known limitation

Docker runtime validation does not exercise the installer, kernel, bootloader
or physical hardware. osCommerce adds no appliance-specific behavior at those
boundaries, so the validated Core 19 baseline supplies inherited evidence.

The App Shop acceptance check replaces the external API with a deterministic
loopback fixture. It proves the authenticated update-discovery request, the
installed revision sent by the application, metadata parsing, and unchanged
application state. It does not prove availability of the external service or
apply a vendor update.

## Deferred issues

No critical or high-severity issue affecting the documented catalog,
administrator, product-management, or update-discovery flow was found. A live
vendor update remains deferred because it requires external service enrollment
and would mutate the disposable appliance. The deterministic fixture covers
the supported authenticated discovery path without claiming vendor service or
update-application coverage.
